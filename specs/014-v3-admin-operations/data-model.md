# Data Model: 014 Admin Operations

Use the Laravel connection from 004–013. Add four ordered migrations: `database/migrations/2026_10_01_000014_create_v3_case_controls.php`, `2026_10_01_000015_create_v3_admin_command_ledgers.php` (also adds the deferred `last_command_id` FK), `2026_10_01_000016_create_v3_review_reminders.php` and `2026_10_01_000017_create_v3_deletion_assessments.php`. Their corresponding behavior tests are authored before each migration. Do not create a parallel user, case, review, provider or export table. UUIDs are server-generated `char(36)`; admin user IDs use existing `users.id` bigint. FKs to case/user/review restrict deletion. One case transaction locks 004's access singleton first for admin mutation, then the 006 case and its control row; it never holds a DB transaction across a bridge/provider call. A shared transactional DB is needed for race tests; PHPUnit's SQLite `:memory:` does not prove two-process ordering.

## `v3_case_operation_controls`

`case_id` UUID PK/FK `v3_processing_cases.id`; `mode` `normal|hold_requested|held|resume_requested|cancel_requested|cancelled` (default `normal`); `control_version` unsigned bigint initially 0; `last_command_id` nullable UUID FK added after the command table; nullable `requested_at`, `applied_at`, `safe_error_code` (004 allowlist); timestamps. There is one row per case, created on first 014 operation under the case lock. `hold_requested|held|resume_requested|cancel_requested|cancelled` is a **claim fence**: no new 007 start, 008–012 effect claim or 013 review decision/correction/route claim may begin. A `resume` remains fenced until its exact Temporal acknowledgement. A pre-workflow case may move directly to `held` or `cancelled` under the case lock because there is no remote workflow to signal. A `cancelled` control is terminal. This is separate from 007 case `state_version`: hold/resume do not insert a case event or invalidate an in-flight worker's precomputed event version. Cancellation inserts one proof-backed `cancelled` case event, increments 007 case version once and in that transaction stales pending/dormant 013 items and clears current review/approval pointers without deleting immutable history.

## `v3_admin_commands`

`id` UUID PK; `case_id` UUID FK; `actor_user_id` bigint FK; `idempotency_key` UUID; `request_sha256` char(64) of canonical validated body; `action` `hold|resume|cancel|retry`; `reason_code` `operator_investigation|service_recovered|abandoned_review|technical_reconcile`; nullable `target_kind` `workflow_start|source_proof|scene_check|scene_jev|review_signal|review_correction`, nullable `target_ref` UUID; `expected_case_version`, `expected_control_version` unsigned bigint; nullable `control_version_after` unsigned bigint; `status` `accepted|dispatching|uncertain|applied|blocked|superseded`; nullable 004-safe `error_code`, `lease_until`, `last_attempt_at`, `applied_at`; `dispatch_attempts` unsigned int default 0; `created_at`, `updated_at`. Unique `(case_id,idempotency_key)` and `(case_id,control_version_after)` for nonnull versions. `retry` requires a target kind/ref and does not change control mode/version; other actions require null target and increment control version once. No raw reason text, content ID, provider ID or credential is stored. Replays compare `request_sha256` after fresh admin authorization. Audit event, delivery rows and any control fence change commit with this row; mutation-audit failure rolls all back.

## `v3_admin_command_deliveries`

`id` UUID PK; `command_id` UUID FK, `case_id` UUID FK; `workflow_id` varchar(160), nullable `run_id` varchar(160); `state` `pending|sending|uncertain|acknowledged|not_started|blocked|superseded`; `control_version` unsigned bigint; `attempt_count` unsigned integer default 0; nullable `lease_until`, `last_attempt_at`, `acknowledged_at`, 004-safe `error_code`; timestamps; unique `(command_id,workflow_id)`. Include the 007 fixed case workflow and every 013 committed correction-workflow ID that is open or start-uncertain at the command fence. A correction start that has not been sent is fenced locally and has no remote acknowledgement requirement; after cancellation its outbox cannot start. Describe a start-uncertain deterministic ID before deciding `not_started`; unavailable history remains `uncertain`. A command is `applied` only after every delivery is acknowledged or proved never started. A newer `cancel` supersedes unconsumed prior hold/resume deliveries under the same case lock without removing their history. This table contains no review note/route payload and makes multi-workflow lost acknowledgements independently reconcilable.

## `v3_admin_operation_audits`

`id` UUID PK; `case_id` nullable UUID FK (null only when an active admin supplied a missing case); `actor_user_id` bigint FK not null; nullable `source_kind` `command|reminder|assessment`, nullable `source_ref` UUID (both null only for denial); `event` `command_requested|command_applied|command_superseded|reminder_posted|assessment_recorded|operation_denied`; `action_code` `hold|resume|cancel|retry|remind|assess_deletion`; nullable fixed `reason_code` from the relevant contract enum; nullable `safe_denial_code` `resource_unavailable|operation_conflict|contract_invalid`; nullable `old_control_mode`, `new_control_mode` from the fixed control enum; nullable `old_control_version`, `new_control_version` unsigned bigint; `occurred_at`; unique `(source_kind,source_ref,event)` for nonnull sources. The service validates same-case source lineage in the insertion transaction; source IDs are opaque audit references, not content IDs. 004 alone audits guest/inactive/wrong-role denials before this service runs. No payload, freeform text, URL, IP, hash, private path, teacher identity or provider error is stored. A mutation event is inserted in the same transaction as its row/state; failure rolls back mutation. A denial-audit failure preserves the safe denial and emits only a fixed emergency code, as in 004.

## `v3_review_reminders`

`id` UUID PK; `case_id` UUID FK; `review_item_id` UUID unique FK `v3_teacher_review_items.id`; `actor_user_id` bigint FK; `idempotency_key` UUID; `request_sha256` char(64); `state` `posted|withdrawn`; `posted_at`, nullable `seen_at`; timestamps; unique `(case_id,idempotency_key)`. One reminder per immutable current dormant item; a second key for the same item is 409. The teacher workspace reads it only through the 004 original-owner path; `seen_at` is an observation, not reassignment or review decision. Admin sees only posted/seen timestamps and opaque review ref.

## `v3_deletion_assessments`

`id` UUID PK; `case_id` UUID FK; `actor_user_id` bigint FK; `idempotency_key` UUID; `request_sha256` char(64); fixed `reason_code` `pilot_cleanup_request`; fixed `policy_version` `pilot-retain-v1`; `status` `deferred_to_015|ineligible`; nullable `safe_blocker` `case_active|workflow_open|review_pending|effect_uncertain`; `case_state_version` unsigned bigint; `control_version` unsigned bigint; `assessed_at`; timestamps; unique `(case_id,idempotency_key)`. The assessment is an immutable audit snapshot, not permission to delete. It contains no private path/hash, retention deadline or freeform reason. `deferred_to_015` means only that the case passed 014's operational precheck at that instant; 015 must independently recheck any later evidence hold and policy before byte deletion. There is **no** 014 purge job or delete route for private artifacts, immutable evidence, accounts or cases.

## Projection and retention

`OperationSummaryV1` is computed, not a stored model: `{case:ClosedSummary,age_seconds,idle_seconds,control_mode,dormant_review_count,uncertain_effect_count}`. The nested `ClosedSummary` is exactly 004's closed scalar DTO; counts are nonnegative bounded database counts, not loaded review/effect objects. `age_seconds` and `idle_seconds` are integer values clamped at zero using DB time. A separate health response reports actual bridge probe result and workflow/review backlogs; it does not assert provider availability from absence of errors. No admin serializer receives a teacher-content model relation.

Retain commands, control transitions, reminders and assessments for the pilot and 015 evidence. Do not delete referenced/uncertain records. Ordinary logs may contain only fixed code, case ID, command ID, action, status, safe count and timing; never request body, source/Section/prompt/scene/note, provider output, private path/hash, account credentials or raw exception.
