# Repository Research and Design Decisions: 014

This is a documentation-only review. I inspected the live V2 files (`routes/web.php`, `bootstrap/app.php`, `app/Http/Controllers/UserController.php`, `app/Models/User.php`, `TeacherAccessMiddleware`, user/permission migrations, `config/filesystems.php`, `phpunit.xml`, auth/feature tests) and the 004–013 prerequisite/015 downstream contracts. The current repository contains no implemented V3 case/Temporal worker. Planned class names must be checked against delivered prerequisite code at T001.

| Finding/decision | Evidence and rationale | Rejected shortcut |
|---|---|---|
| One account authority | 004 already specifies `ChangeAccountAccess::createFromLegacy/updateFromLegacy`, active-admin checks on `/users`, retained-user deletion guard and `/v3/admin/accounts`. V2 `UserController` still writes directly today because 004 is not implemented. 014 tests those actual routes and links to them; it does not add a second account writer. | Another 014 account controller or direct `users.role` update. |
| Closed operational projection | 004 defines exact ClosedSummary keys and safe code allowlists. 007 provides safe case events/counts; 013 provides dormant/outbox state. 015 owns exports. 014 wraps the closed DTO with named scalar fields and exposes no general model/metadata serialization or export. | Reusing owner serializers, raw exception/provider error or arbitrary model relations. |
| Separate control version | 007 `(case_id,event_key)` and `state_version` are an ordered immutable event stream. A hold/resume event inserted between worker callbacks would make an already prepared 007 callback stale. 014 uses its own control version/fence; only proof-backed cancellation changes terminal case state. | Editing case status directly or advancing 007 version on every admin click. |
| Terminal retry boundary | 007 fixed `v3-case-{case_id}` identity is reject-duplicate and 007 blocked/failed are terminal. 008 NotebookLM create/add and 010/011 generator effects have one-send uncertainty ledgers; 012 checker/JEV is read-only and bounded; 013 signals and correction workflow use stable IDs. Therefore an admin retry can reconcile the **same** permitted operation, but cannot invent a new terminal-run resume or repeat an uncertain external send. | Generic “retry blocked case” button that starts a new workflow or calls the provider again. |
| Two-phase hold/cancel | A Temporal signal can be lost or arrive while a provider call is in flight. Laravel must commit a case-locked local claim fence/audit first, then deliver a versioned signal and accept only proof from the same workflow. A known late result may be retained privately but cannot start a new claim after cancellation. | Marking cancelled merely after HTTP 202, or discarding known evidence. |
| Real health versus backlog | Current 007/013 records reveal queued/uncertain work, not live vendor health. A signed bounded Temporal RPC can prove bridge reachability; provider health remains `unknown`. Keep backlog counts separate to avoid claiming a service is healthy merely because no case failed. | Inferring provider availability from zero errors or exposing raw probe exceptions. |
| Reminder and account preservation | Conversation 23 permits admin reminders but says a disabled teacher's review stays with that teacher. 013 provides current dormant items and owner workspace alert; a fixed in-app reminder row can be shown to only that owner. | Admin note text, email without authorization, review reassignment or admin approval. |
| Pilot retention handoff | 014's original draft says no automatic deletion and defines no retention period. 013 retains review/uncertain evidence; 015 owns retention-aware history/export and speaks of later deleted artifacts. 014 records an assessment under `pilot-retain-v1` with no physical purge; any later deletion requires a separate concrete 015 rule and fresh eligibility check. | Choosing an arbitrary number of days, deleting a private prefix by case ID or erasing immutable audit. |

The active Spec Kit selector points to 004; the read-only `speckit-analyze` prerequisite script therefore did not analyze 014 automatically. I performed the skill's semantic requirement/plan/task pass directly on 014 before edits, then recorded findings in [review-report](review-report.md). `.specify/memory/constitution.md` is an unratified template. No selector change was needed.
