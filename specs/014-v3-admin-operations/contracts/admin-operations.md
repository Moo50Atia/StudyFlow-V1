# Contract: 014 Admin Operations v1

Read with [model](../data-model.md), [acceptance cases](acceptance-matrix.md), [004 access](../../004-v3-access-ownership/contracts/access.md), [007 workflow](../../007-v3-workflow-progress/contracts/workflow.md) and [013 review](../../013-v3-teacher-review/contracts/review.md). 014 extends the 004 closed projection with a separately named, explicitly scalar wrapper. It never passes Eloquent models, provider payloads or arbitrary exception text to an admin serializer.

## Admin HTTP and privacy boundary

Append only the routes below to 004's `routes/v3.php` under active-admin web-session middleware, CSRF on mutations and `Cache-Control: private, no-store` on every success/error/denial. Check authentication → fresh 004 active admin → case existence → validated exact body → same-key canonical replay → expected versions/eligibility for a **new** key → mutation. The replay must still match the case and nested review path and must never bypass current actor eligibility; it returns its committed result even if the case later changed state. JSON errors use `{error:{code,message}}`: guest 401 `unauthenticated`, inactive/wrong role 403 `access_denied` and missing case/child 404 `resource_unavailable` reuse 004's fixed messages; malformed/extra business fields get 422 `contract_invalid` / “Invalid operation request.”; stale or forbidden state gets 409 `operation_conflict` / “Operation changed. Reload and retry.”; DB/audit/bridge outage gets 503 `operation_unavailable` / “Operation is temporarily unavailable.” Browser GET is HTML, successful POST redirects 303 to `/v3/admin/operations/{case}` with a generic status, validation redirects using Laravel, CSRF remains 419. A missing case and a fabricated ID have identical 404 bodies. An admin never gets a teacher-owned content route through these handlers.

Constrain `{case}` and `{review}` path parameters to canonical UUIDs and register `/health` before the case-detail route; malformed IDs are 404. `OperationSummaryV1` has exactly `{case:{case_id,stage_code,status_code,error_code,created_at,updated_at,attempt_count,scene_count,approved_scene_count},age_seconds,idle_seconds,control_mode,dormant_review_count,uncertain_effect_count}`. Use the 004 closed scalar constructor for `case`, then separately count only 013 current dormant items and unresolved 008/010/011/012/013 effect/outbox rows. Counts may be zero; do not include effect payload, route note, source ID or model relation. `control_mode` is the fixed 014 enum. `action_targets` only includes `workflow_start|source_proof|scene_check|scene_jev|review_signal|review_correction` currently eligible for the exact reconciliation rules below. Unsupported 004 codes or a corrupt projection fail closed with 503, not a raw serialized row. There is no 014 export route; 015 must consume this closed projection or a stricter one.

`v3_admin_operation_audits` is the only new 014 audit store: fixed `command_requested|command_applied|command_superseded|reminder_posted|assessment_recorded|operation_denied` events with active admin actor ID, case ID if resolved, source row ID if committed, fixed action/reason/denial code, old/new control mode/version and DB time. 004 alone audits guest/inactive/wrong-role denials before an admin service runs. The 014 row stores no request body, raw URL/query, content/teacher identity, note, digest, path or exception. Requested/applied/reminder/assessment audit writes are in their corresponding DB transactions; a failed write rolls back that mutation or acknowledgement. A denial audit failure retains the fixed HTTP denial and emits one fixed emergency log code without request data. Replays do not create another audit row.

## Command transaction and state matrix

`AdminCommandV1` is exactly `{schema_version:1,idempotency_key:UUID,expected_case_version:positive_integer,expected_control_version:nonnegative_integer,action:"hold"|"resume"|"cancel"|"retry",reason_code:"operator_investigation"|"service_recovered"|"abandoned_review"|"technical_reconcile",target_kind:null|"workflow_start"|"source_proof"|"scene_check"|"scene_jev"|"review_signal"|"review_correction",target_ref:null|UUID}`. `retry` requires `technical_reconcile` and both target fields; other actions require null targets. `hold` uses `operator_investigation`, `resume` uses `service_recovered`, and `cancel` uses `operator_investigation|abandoned_review`. No freeform reason, owner, status override, provider key, scene ID or settings override is accepted. Canonical fixed-key-order JSON after validation is hashed as `request_sha256`; authenticate before looking up `(case_id,idempotency_key)`. Exact same-key/body replay returns the prior row even after state advances; changed body 409. A new key with stale case/control version 409. Under 004 access singleton → case → control row locks, recheck active actor, state, target lineage and versions; insert command and safe audit, update control fence if applicable, commit. DB/audit failure leaves no command/fence and makes no bridge call. A new case control row is created inside this transaction if absent.

| Action | Permitted precondition | Committed local effect | Remote/reconciliation outcome |
|---|---|---|---|
| `hold` | Nonterminal case state `awaiting_workflow|queued|running|awaiting_review` with `normal` control; no current approved complete case | Increment control version, `hold_requested` (or `held` before 007 workflow start); fence new claims immediately | Signal every matching open case/correction workflow; query exact version/command. On all proofs mark `held`. In-flight claimed effect may finish as evidence. |
| `resume` | `held`, same case not terminal, current admin and expected versions | Increment version, `resume_requested`; keep fence | Signal same workflow; exact proof changes to `normal`. Before workflow start, local `held→normal` after one transaction. No active-settings switch. |
| `cancel` | Nonterminal case and control not already `cancel_requested|cancelled`; `complete/approved`, `blocked` and `failed` are not cancelable | Increment version, `cancel_requested` and fence (or direct `cancelled` if workflow never started); preserve 013 review/approval/effect history | Matching live workflow acknowledges command by signed callback before exit. Laravel proof event makes case `cancelled`; timeout stays `cancel_requested/uncertain`. No substitute workflow ID. |
| `retry` | `normal`, nonterminal case, one exact recoverable target returned by operations detail, no prior newer target or exhausted budget | Immutable command/audit only, no case/control version change | Invoke existing ledger's same-ID reconciliation. `applied` means a verified readback/signal outcome, **not** a new provider send or terminal restart; unresolved remains `uncertain`. |

No hold/resume/cancel command may target a correction workflow by arbitrary browser ID. The case's 007 fixed `v3-case-{case_id}` link and 013's committed correction-workflow IDs are resolved server-side under the fence. Insert one `v3_admin_command_deliveries` row per open or start-uncertain deterministic workflow in the command transaction; each row is described and signalled independently with the same command/version, and all require proof before the command is applied. Direct local `held`/`cancelled` is allowed only when the 007 start has never been attempted and no 013 correction start has been attempted; any start-uncertain ID must first be described. A committed but unsent correction start is fenced locally; cancellation blocks that outbox from starting. If a possibly open workflow cannot be described or Temporal is unavailable, leave its delivery uncertain and the local fence active. A newer `cancel` may supersede an unconsumed `hold`/`resume` under the case lock: retain the old command/deliveries as `superseded`, send the higher control version, and ignore any late lower-version acknowledgement without clearing the cancel fence. A closed workflow is never restarted to apply an old command. Cancellation of a case with no started or start-uncertain workflow is local and emits the same proof-backed `cancelled` event under the case lock. A terminal `complete/approved` case is changed only through the original teacher's 013 post-approval correction, never admin cancel/retry.

The 014 `CaseOperationGuard` checks control mode under the case lock **inside** every 007 start and 008–013 effect/review claim transaction. In `hold_requested|held|resume_requested|cancel_requested|cancelled`, it denies a new external send/repair/revision/teacher decision through that prerequisite endpoint's **existing** safe 409 conflict code; 013 owner decisions keep `review_conflict`, rather than inventing a new 013 response shape. Read-only owner views and private evidence readback may continue under their own authorization. Add signed `GET /api/internal/v1/cases/{case_id}/operation-control` with exact `{data:{mode,control_version}}`; HMAC failure 401, missing case 404, DB failure 503, all no-store. A worker receiving a claim conflict queries this operation-control endpoint to distinguish hold/cancel from a stale input, then parks or exits without another send. Extend the real 007 `StartWorkflow`, 008 `SourceEffectLedger`/activation, 009 lesson query claim, 010 prompt/feedback/JEV claims, 011 coding claims, 012 check/JEV/repair claims and 013 decision/correction/route claims. A result for an effect claimed **before** the fence may be recorded once with its normal digest/evidence validation; while held it cannot launch the next claim, and after cancellation it cannot change the current case/Section tip or issue an approval. A late 007 worker milestone after a proved cancellation is 409 and retained only as worker evidence, never a case-state regression. Reconciliation does not infer a provider result from absence of a response.

## Temporal delivery and retry targets

Extend 007's signed private bridge with `POST /internal/v1/workflows/{workflow_id}/admin-controls` body exactly `{schema_version:1,case_id,command_ref,control_version,action:"hold"|"resume"|"cancel"}` → 202 `{data:{command_ref,state:"accepted"}}`; and `GET /internal/v1/workflows/{workflow_id}/admin-controls/{command_ref}` → 200 `{data:{command_ref,control_version,state:"pending"|"applied"|"closed"}}`. The workflow stores only opaque case/command/version/action in deterministic history; it ignores lower versions and exact duplicates. Changed replay of one command ID is 409. On consumption, a signed worker callback `POST /api/internal/v1/admin-control-results` with exactly `{schema_version:1,case_id,workflow_id,run_id,command_ref,control_version,outcome:"held"|"resumed"|"cancelled"}` is validated against the committed command/fence and matching delivery row. Each callback marks one delivery acknowledged; the **last** required acknowledgement atomically applies the aggregate control state and, for cancellation, inserts one proof-backed 007 `cancelled` event. In that same cancellation transaction, mark all 013 pending/dormant review items `stale`, clear every Section current review/approval pointer and set those Section states `blocked` with null safe error; preserve all immutable decisions, approvals, notes and candidates. Thus owner review/reminder actions cease and `approved_scene_count` becomes zero for the cancelled case. A callback for a superseded lower control version returns the historical result without changing current mode. A workflow may close only after its own callback commits; the case is not cancelled until every required workflow is accounted for. Hold/resume callbacks do **not** increment 007 case state version. Bad HMAC 401 before lookup, missing/mismatched identity 404, changed replay/stale version 409, invalid shape 422, bridge/DB unavailable 503; fixed no-store bodies. `GET /internal/v1/health` uses a real bounded Temporal RPC and returns `{data:{reachable:true,checked_at}}` or 503, with no namespace details or secrets.

Schedule `php artisan v3:dispatch-admin-commands` each minute. Claim each pending/uncertain delivery row with a two-minute DB lease; a second dispatcher skips it. Before POST, describe/query that fixed workflow/command. Matching applied proof marks that delivery acknowledged; unknown response remains uncertain and is queried again; verified not-consumed may resend **the same** command ID/version/body. Only after all delivery rows acknowledge or prove never started may the aggregate command become applied and the hold/resume/cancel control transition finish. If a workflow closed without required cancellation proof, mark its delivery blocked `internal` and alert; never mark the case cancelled or start another run. No transaction spans HTTP. In-flight external sends already reserved by 008/010/011/013 retain their one-send ledger semantics despite a cancellation. Repeated dispatch never increments a provider send count.

`retry` commands are claimed after commit with the same two-minute command lease, but create no Temporal-control delivery rows. `ReconcileAdminTarget` records `applied` only for a verified existing outcome, `uncertain` for an unresolved readback and `blocked` only for a proven terminal target; an exact command replay does not invoke the target again. Targets are deliberately narrow. `workflow_start` calls 007 fixed-ID describe/reconcile; `source_proof` calls 008 inventory/content **read** reconciliation only; `scene_check|scene_jev` asks 012 to advance only a remaining bounded read-only technical attempt on the exact current candidate; `review_signal` queries/resends the same 013 decision ID; `review_correction` describes/adopts the same deterministic 013 correction workflow ID. A target that is stale, terminal, non-current, mismatched, budget-exhausted or has no complete lineage is 409 before command insertion. 010/011 generated-text sends, 008 `notebook_create`/`notebook_add_text` and uncertain one-send repair effects have **no** 014 resend target. An existing reconciler may return `uncertain` honestly; admin cannot force-confirm, insert JEV results or choose another model.

## Reminder, account and deletion handoff

A reminder requires a 013 Section-current `dormant` review item and exact expected item version under case/Section lock. Insert one `v3_review_reminders` row plus safe audit in the same transaction; unique review-item key prevents a second reminder. Only the 004 active original teacher's 013 review-index HTML query reads that row; it displays fixed text “A scene is ready for your review” and the already-authorized owner review link, never a note or admin-authored text. The existing exact 013 JSON review-list shape stays unchanged. Disabled teacher remains owner; alert appears only after restoration. Missing/foreign/noncurrent item is 404; a still-current item that is no longer dormant, has a mismatched version or already has a reminder under a different key is 409. No email or external messaging.

Account provisioning uses 004's existing `GET /v3/admin/accounts`, `PATCH /v3/admin/accounts/{user}/access` and legacy admin `GET /users/create`, `POST /users`; 004 `ChangeAccountAccess::createFromLegacy/updateFromLegacy` is the sole actor/role/access writer. 014 adds no `AccountController` or duplicate account API. The V2 `/users` form remains an identity surface: it must recheck 004 active admin and retain 004's self/final-admin, enrolled-credential and deletion guards. A disable event leaves `v3_processing_cases.owner_user_id` and pending/dormant 013 reviews untouched. 005 settings routes remain 005-owned.

Deletion assessment checks the same active-admin gate and exact replay before a case snapshot. `deferred_to_015` requires terminal `cancelled|blocked|failed|complete/approved`, verified no open 007/013 workflow, no current pending/dormant review and no uncertain 008/010/011/012/013 effect or command. Otherwise record `ineligible` with the first fixed blocker in order `case_active→workflow_open→review_pending→effect_uncertain`. No 014 request actually deletes content or immutable metadata. `pilot-retain-v1` has no automatic deadline; 015 later defines a reviewed physical-retention rule and must recheck all evidence holds, not trust this old snapshot. Denied and deferred assessments remain auditable; exact replay returns the same snapshot. Admin gets only safe status/blocker, never the artifact list.
