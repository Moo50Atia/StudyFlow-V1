# Feature Specification: V3 Prompt Generation and JEV Qualification

**Feature:** `010-v3-prompt-jev-qualification`  
**Status:** Reviewed design; implementation prerequisites and live gates remain  
**Authority:** Conversation 23, later owner corrections, and [009's canonical prompt contract](../009-v3-lesson-map-sections/contracts/lesson-structure.md). V2 is reference only.

## Boundary and outcome

For each complete 009 First-step Section, 010 records an immutable original Third-step scene prompt, obtains one typed JEV Choice/Score/Noul decision for each evaluated version, and, when permitted, creates bounded successor versions with the case-captured feedback provider/template. A passing **current** version becomes an opaque, private input to 011. The original teacher reviews the final scene under 013, not the prompt. Other teachers and admins cannot read prompt bodies, Section bodies, raw JEV answers or feedback.

009 owns the map, all eleven First fields, canonical bytes, lesson cursor and literal `Continue`; 010 owns Execution/Second/Third processing, original Third-output persistence, prompt versions, JEV and revision. Laravel owns identities, settings, records and authorization. Temporal schedules durable activities and carries only safe IDs/status. 010 neither adds KOS/KIE, a tenant model, a source mapper, a teacher prompt approval, nor a second model to judge a successful typed JEV answer.

## Requirements

- **FR-001 — Canonical later steps.** Use the exact Execution Protocol, Second and Third bytes/digests from 009 on the same source-bound NotebookLM conversation. After 009's first First result, send Execution once for the first work item. If its answer is only `System Ready`, send Second and Third once; if it already contains complete exact-work Second/Third output, reuse those turns without another send. For a later work item, inspect the recorded `Continue` answer first: complete unambiguous Second/Third output is reused; First-only output leads to one Second and one Third send. Partial/ambiguous later-step output is `validation` and never guessed or blindly repeated. A live selected-adapter round trip is a release gate for these forms.
- **FR-002 — Section and completion lineage.** Require the exact current ordered 009 Section set and all eleven nonempty-required First fields, preserving their values. Parse one Second mapping and one Third prompt per Section, matching `Lec<X> (Sec<Y>)` to 009's work ordinal and Section ordinal. Persist raw turns and immutable original prompt versions before sending 009's exact completion receipt with one durable Third-output ref per Section. A missing/extra/duplicate Section, malformed scene type or changed cursor blocks the receipt.
- **FR-003 — Typed evaluation.** For each current prompt version, send the same Section's First fields, prompt and recorded source lineage as untrusted data in one named JEV request containing `choice`, `score`, `noul`. Apply the captured 005 rule directly to a successful well-formed typed response. Noul yes is probability ≥0.5; for a yes answer its probability is its confidence. No extra model decides usability. Wire-schema/transport/auth failures yield no verdict and use technical handling, not a low score.
- **FR-004 — Evidence.** Record immutable request digest, exact model returned, named typed values, probabilities/confidences where provided, captured settings/checksum, question/rule versions, numeric comparisons, decision and timestamps. Keep raw evidence private; safe progress/admin projections expose only allowlisted stage/status/error codes.
- **FR-005 — Same-Section revision.** A valid nonpassing decision with Choice `revise` or another threshold failure **must** invoke the captured feedback provider with the exact approved feedback template and failed criteria when revision budget remains. It produces a new immutable version linked to the previous version and same Section. Choice `block` is terminal for that Section. Feedback text cannot change source fields, canonical prompts, settings or Section identity. Every new version is evaluated by JEV before 011 sees it.
- **FR-006 — Bounded current pass.** `limits.prompt_revisions` is the maximum number of successor versions after original, including 0. Equality to score/confidence threshold passes; no rounding. At most one current passing version per Section can be handed to 011; a superseded passing version cannot be reused for a later authoring request. Exhaustion records Section `blocked/policy_denied`, permits other Sections to progress, and sends no coding request for the blocked Section.
- **FR-007 — Effects and recovery.** Claim each stateful NotebookLM turn and feedback generation effect durably before send; never automatically resend after a possibly delivered call. Exact duplicate callbacks return the committed result, changed replay/stale cursor conflicts, and uncertain outcomes remain visible for reviewed recovery. Pure JEV evaluation may retry the identical request within captured technical budget; first committed valid answer determines the immutable verdict. Storage failure never creates a completion or pass without its private artifact.
- **FR-008 — Security and retention.** Only 007 HMAC worker calls can obtain private 010 context or write effects; verify signature before ID lookup and bind every ref to one case/work/Section. Preserve 004 original-owner restrictions on existing teacher routes and closed admin DTO. Never expose V3 refs through V2 `/sections`, `/lectures`, `/api/lectures` or `teacher-study-flow`; do not add prompt-content user routes. Keep rows/artifacts and uncertain attempts for pilot history; 015 defines deletion after reconciliation, with no 010 delete endpoint.

## Acceptance and completion

The [acceptance matrix](contracts/acceptance-matrix.md) gives stable P01–P18 scenarios, requirements, test files and expected outcomes. `SC-001`: 010's signed 011 handoff returns a prompt only when it is the current version with a stored passing JEV decision for the same case/Section; 011 must bind that ref to each authoring request. `SC-002`: every 009 receipt points to the exact persisted original Third refs. `SC-003`: duplicate/racing claims yield one stateful send and one immutable result; technical failures never become policy failures. `SC-004`: owner/admin/V2 access probes cannot reveal prompt content. Evidence is executable contract, integration, two-process concurrency and live selected-provider tests listed in [quickstart](quickstart.md); a mock alone does not prove live integration.

## States and user-visible behavior

Each Section has `awaiting_prompt → awaiting_qualification → qualified | revising | blocked`; `revising → awaiting_qualification | uncertain | blocked`; a technical call can leave `uncertain` without an invented verdict. 009 lesson progression may continue after every original Third output is durable even while Section qualification proceeds. Partial success is valid: qualified Sections can reach 011; blocked/uncertain ones cannot. 007 teacher progress uses safe `prompting|prompt_qualification` stages and `queued|running|blocked` statuses; 010's original-owner `/prompt-status` lists each Section's safe state/error/revision count. Error codes are fixed `validation|provider_unavailable|timeout|policy_denied|internal`; admin sees only 004's scalar case projection. No teacher-facing prompt edit/approval action exists.

## Dependencies and live gates

Entry requires implemented 004–009 contracts, active 005 captured settings with approved feedback template, 007 workflow/HMAC transport, 008 bound source, and 009 current `awaiting_010` cursor. NotebookLM's bound conversation produces the original final Section prompt through canonical Third. The captured `providers.prompt` descriptor is not invoked by 010; `providers.feedback` is used only for failed-prompt revision. 011 consumes the qualified-prompt handoff; 012–015 remain downstream. Live selected-adapter/provider and account access gates remain before implementation completion; this documentation review does not claim runtime proof.
