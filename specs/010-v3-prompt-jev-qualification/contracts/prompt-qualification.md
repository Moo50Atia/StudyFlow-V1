## Canonical cycle and parser

Load Execution, Second and Third as exact UTF-8 fenced-block bytes from 009, checking SHA-256 `5ab2448f34c9b2b90199347772d10d7d217ba9fd468dffc28e3169bd0a7fdce9`, `a8776affc821a1b913a4685b309dc0304afc03c7389fcfe44b366b6f5683f203` and `07798d744b973ec11248897d2efe0e769ab481c4a21cce7562696dd131217955`. Never edit their text. After 009 records the first work's First Sections, 010 uses that current 008-bound conversation and `query_once` to send Execution exactly once, recording its response and conversation. Accept either a trimmed exact `System Ready` response, then send Second and Third once each in sequence, or a response already containing complete First/Second/Third material for the same work. In the combined case, verify the First fields equal 009's stored Section values, then record Second/Third as `execution_reuse` with no new sends. Partial/other Execution responses block safely; do not repeat Execution. Work ordinal X in `Lec<X>` is 009's `work_ordinal`, including a promoted Mini Chapter; Y is `v3_teacher_sections.ordinal_in_work`. The `Lecture:` value must be exactly `W{work_ordinal} | {full 009 map path}`, matching the current First header. 010 never sends `Continue` or changes 009's cursor.

For later work, 010's signed context includes 009's recorded raw `Continue` answer and query ref. Parse it before any send. The accepted combined form is three consecutive `Lecture: W{ordinal} | {path}` segments: complete 009 First fields, complete Second placeholders, complete Third scene prompts, all for the same exact Section ordinals. Record the latter two as `continue_reuse` turns with `send_count=0` and the same 009 origin query; final conversation is the recorded Continue `conversation_out`. The other accepted form contains only the complete First segment, followed by one sent Second and one sent Third. Two segments, ambiguous headers, another work ordinal or a partial Section set mark 010 `blocked/validation`; do not infer completion or resend a canonical step to patch a partial combined answer. A trailing canonical completion marker is permitted only when its X equals the current 009 work ordinal; it is excluded from the Third prompt body. It is not required from a separately sent Third because that canonical body requests prompts only. Live tests must prove the selected NotebookLM adapter's actual behavior. The raw combined answer remains 009-owned; 010 retains a verified private copy for exact-turn lineage.

For a separately sent Second/Third step, the parser accepts one `Lecture: W{work_ordinal} | {full 009 map path}` header and one numbered `Lec<X> (Sec<Y>):` block per exact current Section, in ordinal order. In combined Execution or Continue answers, apply this same parser separately to the second and third segments after the verified First segment. Second blocks contain a nonempty quoted placeholder; Third blocks contain a nonempty quoted prompt whose first token is exactly one of `Process`, `Comparison`, `Accumulation`, `Parallel Flow`, `Time Evolution` followed by whitespace/punctuation. A block ends at the next numbered header or end of its segment; strip only outer matching quotes and surrounding whitespace, preserve interior bytes, reject an unmatched quote, duplicate/extra/missing block, unknown scene type, content outside the allowed segments or >65536-byte prompt. This is a structural generation contract, never a second judgment of JEV's successful typed response. Every First Section has exactly all eleven 009 fields; only `laws_if_any` may be explicitly empty. Do not synthesize concepts or merge Sections. A parser error makes no version 1/009 receipt.

After exact Third parsing, write all original version-1 artifacts and rows under the work-item lock in a single DB transaction after atomic private file writes. Verify each artifact digest, original Section set and cursor version before constructing the 009 completion digest exactly as 009 defines it. Persist the immutable `completion_ref` and digest on the work item, then POST the exact receipt to 009. Retry only the same receipt after a lost HTTP acknowledgement; 009's exact replay is safe. `originals_ready` without a receipt is reconciled from stored rows and the same receipt, never by another NotebookLM send. 009 may advance to the next Lesson after this receipt while JEV runs per Section. A blocked qualification does not retroactively invalidate original Third evidence.

### Stable digests and IDs

`section_fields_sha256` is SHA-256 of UTF-8 `010-section-v1\n` followed, in the eleven column order listed in `prompt-context`, by `field_name\n<byte_length>:<exact_LF_normalized_value>\n` for each field. This includes the explicitly empty `laws_if_any`. A turn request digest is SHA-256 of UTF-8 `010-turn-v1\n` plus newline-separated case ID, map ref, decimal work ordinal, step, canonical digest, comma-joined ordered Section refs, origin, origin query ref or empty string, origin turn ref or empty string, and `<byte_length>:<conversation_in>`. Laravel recomputes; it does not trust a caller digest. `completion_ref` is exactly `prompt-work-{work_item_uuid}`; compute `completion_sha256` by 009's published grammar, using exact ordered version-1 IDs.

The question asset `resources/v3/jev/prompt-questions-v1.json` contains the exact named questions/101 Score criteria below as UTF-8 JSON; both PHP and Python read the same file, check its `question_sha256`, and never generate divergent text at runtime. The JEV request digest is SHA-256 of `010-jev-v1\n` plus newline-separated prompt-version UUID, prompt body SHA, Section fields SHA, captured settings checksum, question SHA and requested model. Feedback request digest is SHA-256 of `010-feedback-v1\n` plus newline-separated failed version UUID, qualification answer SHA, captured template SHA, provider ID, provider model and credential-ref label. Laravel computes these from stored evidence and compares supplied values. For a successful JEV result, `answer_sha256` is SHA-256 of the exact UTF-8 JSON response representation supplied in the signed result; retain that representation privately and parse its typed fields. Duplicate-result equality compares its digest and response model, never a caller decision flag.

## JEV request, direct rule and feedback

The current [official OpenAPI](https://api.typesafe.ai/openapi.json) defines `POST /v1/systemone` Bearer `{state,model,questions}` and `GET /v1/models`. Deployment supplies `TYPESAFE_API_KEY` and explicit `JEV_MODEL`; verify the name is returned by `/v1/models` at live gate. The state is a JSON object `{section:{the eleven exact First fields},coverage_pages:[integers],prompt:<exact version body>}`. Fields/prompt are quoted data, never tool instructions. Questions are named exactly `choice`, `score`, `noul`, all sent together. Version `prompt-questions-v1` fixes:

- `choice`: criteria keys exactly `pass` = grounded in Section, one focused visual goal, allowed scene type and misconception correction; `revise` = a correctable omission/clarity/visual error; `block` = irreconcilable source contradiction or unsafe/unrelated content. Instructions: `Classify the prompt against the supplied Section; return one of the named choices.`
- `score`: instructions `Rate the prompt's source fidelity, coverage, visual clarity, misconception correction and final visual learning outcome on the requested 0–100 levels.` Criteria is an array of 101 ordered level strings (index is score) constructed deterministically as `n/100: ` plus the band description: 0–19 `contradictory or missing learning scene`; 20–39 `major source or coverage gaps`; 40–59 `partial scene without clear misconception correction`; 60–79 `grounded visual scene with notable gaps`; 80–100 `grounded, complete, focused visual explanation`. Persist the exact request digest/criteria; do not rescale a smaller rubric after the fact. The provider's `score` is a fractional probability-weighted expected score on 0–100.
- `noul`: instructions `Does this exact prompt remain supported by the supplied Section and visually correct its key misconception?`; criteria true = `Both source support and visual correction are present`, false = `Either is absent or contradicted`.

Require exactly the three named answers and matching `type`; Choice has allowed `choice`, finite `confidence` in [0,1] and expected probability keys; Score has finite `score` in [0,100], finite `confidence` in [0,1], 0–100 legend/probability levels; Noul has finite `noul` in [0,1]. This validates the vendor's typed wire shape, not the quality of its judgment. Per owner correction, Noul yes is `noul≥0.5` and its yes-probability itself is the confidence for a yes answer. Pass iff `choice=pass AND score≥min_score AND 100*choice.confidence≥min_confidence AND 100*score.confidence≥min_confidence AND noul≥0.5 AND 100*noul≥min_confidence`. Compare unrounded source values. Choice `block` yields `block` even if other values pass; any other failed check yields `revise` if budget remains, otherwise `block` with `revision_budget_exhausted`. Capture failed check codes `choice|score|choice_confidence|score_confidence|noul|noul_confidence|revision_budget_exhausted`; no prose from JEV is trusted as a decision rule. A typed, in-range low answer is a valid policy verdict; malformed/missing wire is a technical failure with no verdict. Do not call a second suitability model.

For revision, load `ApprovedTemplateRepository::getCaptured(id,checksum)` exact bytes and the captured `providers.feedback` descriptor from the case's settings version. The model input is `{template_bytes,section_fields,previous_prompt,failed_check_codes,typed_JEV_values,section_ref}` with Section/prompt explicitly marked as untrusted data. It may emit **only** a replacement prompt body for that same Section; no changed Section fields, tool request or owner ID is accepted. Retain the original and every successor. A technical failure before a provider send uses captured 007 retry policy; a timeout after claim stays uncertain. No production default template or fallback provider is invented. The 005 payload still requires and captures `providers.prompt`, but 010 does not call it: the later explicit owner decision supersedes 005's older downstream-use description. Do not silently route Third output through that model or fabricate a use to satisfy a settings field.
