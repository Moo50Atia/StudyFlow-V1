# Contract: 007 Workflow Start, Milestones and Progress

**Version:** 007-r1. 004 supplies current role/owner checks and closed admin DTO; 005 supplies `SettingsVersionRepository::getCaptured`; 006 supplies a ready same-owner Document and a case initially `awaiting_workflow`, `state_version=1`. The worker never receives PDF bytes, extracted text, prompt, scene, review note, teacher name/email or an admin session.

## Deployment and trust boundary

007 introduces `v3_engine/` (Python 3.12, Temporal Python SDK, FastAPI bridge), a Temporal namespace configured by `V3_TEMPORAL_ADDRESS`, `V3_TEMPORAL_NAMESPACE`, task queue `v3-cases`, and a private bridge URL `V3_BRIDGE_URL`. The Python bridge listens only on loopback/private network; use TLS when crossing hosts. Laravel's start client and Python's callback client use **different** environment secrets `V3_BRIDGE_HMAC_KEY` and `V3_CALLBACK_HMAC_KEY`; neither is stored in settings/DB or logged. No browser route reaches the bridge. Missing secret/namespace/worker fails closed.

For every internal HTTP request, sign raw bytes using lowercase hex HMAC-SHA256 over `METHOD + "\n" + exact_path_without_query + "\n" + decimal_unix_timestamp + "\n" + lowercase_sha256(raw_body)`. Headers: `X-V3-Timestamp`, `X-V3-Signature`, `X-V3-Contract-Version: 1`; JSON content type for POST. Verify ±300 seconds and constant-time signature before parsing body or looking up an ID. There is no query string on these endpoints. Replay within five minutes is safe only because start uses a fixed workflow ID and callback uses an event key; tests must prove both. Internal 401 `worker_unauthenticated`, 422 `contract_invalid`, 409 `workflow_conflict`/`event_conflict`, 503 `workflow_unavailable` use fixed bodies `{error:{code,message}}` with no exception/tool text.

| Laravel → Python `GET /internal/v1/workflows/{workflow_id}` | Exact deterministic ID in path, signed empty body | 200 `{data:{found:boolean,workflow_id,run_id:null|string,temporal_status:null|"open"|"completed"|"failed"|"cancelled",case_id:null|UUID,settings_version_id:null|integer,settings_checksum:null|lowercase_sha256}}` | 503 on Temporal unavailability; not-found is only a verified Temporal result |
| Python → Laravel `POST /api/internal/v1/case-events` | Exact `WorkerEventV1` below, signed with callback key | 201 `{data:{event_id,case_id,state_version}}`; exact duplicate 200 same data | 404 for unknown case/link, 409 for mismatched identity/key payload or stale version; 422 for unsupported code/schema |

Laravel loads the callback in a new `routes/api.php` through `bootstrap/app.php`'s API routing; it has no web session or CSRF and uses dedicated HMAC middleware. Do not mount it under 004's `routes/v3.php` or the legacy `/api/lectures` route. Python uses the SDK `Client.start_workflow` with `WorkflowIDReusePolicy.REJECT_DUPLICATE`, default fail-on-running conflict (not terminate or use-existing), `retry_policy=None`, fixed task queue and memo containing exactly `case_id`, `settings_version_id`, `settings_checksum`, `schema_version=1`. On already-started, describe the fixed ID, compare memo and return its original run ID/status. A closed run is never replaced. Workflow input is exactly `{case_id,settings_version_id,settings_checksum,retry_policy,schema_version:1}`; Laravel obtains these nonsecret values from the checksum-verified 005 captured row before POST. Python never reads the active settings pointer or the Laravel database. Neither input nor memo contains owner/document IDs or content. A missing/mismatched case ID, settings ID or checksum memo is `workflow_conflict`, never adoption. Persist the verified checksum on the link before first POST.

`WorkerEventV1` contains exactly `{schema_version:1,event_key:string,case_id:UUID,workflow_id:string,run_id:string,expected_state_version:positive_integer,event_type,stage_code,status_code,error_code}`. `event_key` is ASCII `[a-z0-9:_-]{1,128}`, stable across activity retries. `event_type` in 007 production is `workflow_started`, `stage_started`, `stage_completed`, `workflow_failed`; later review/approval/cancel producers require their own provenance checks. Stage codes are the 004 allowlist. `status_code` is the 004 allowlist; 007 accepts `queued|running|blocked|failed` through this worker route, never `awaiting_review|approved|cancelled`. `error_code` is null or the 004 allowlist and is mandatory non-null for `blocked|failed`. Initial callback is exactly key `workflow_started`, expected version 1, type `workflow_started`, stage `extraction`, status `queued`, error null. `stage_started` must be `running`; `stage_completed` may be `queued` (next work remains) or `running` (other work continues). Worker `workflow_failed` must be `failed` with a safe error. These event types never assert that a candidate is qualified or a review approved.

Each callback activity attempt computes a fresh HMAC timestamp/signature over the same serialized `WorkerEventV1` body; it does not reuse an expired signature. The event key and payload bytes remain stable across retries. A bridge start retry likewise re-signs its unchanged request body.

## Start discovery and uncertainty

`php artisan v3:dispatch-workflows` is scheduled every minute. It queries committed 006 cases in `awaiting_workflow`, creates one `v3_workflow_links` row under case lock and dispatches `StartCaseWorkflowJob` after commit on a dedicated `v3_workflow` database queue (`after_commit=true`, worker timeout 30 seconds, `retry_after=90`, job `tries=1`). The link exists **before** any remote request. A case created just before a scheduler crash is found on the next run. The same command also describes `started` links whose `last_reconciled_at` is at least five minutes old, including cases no longer `awaiting_workflow`, to detect a closed failed/cancelled execution and update Laravel safely. Claim due `pending|uncertain` links with a two-minute lease using compare-and-set; a duplicate job exits. Never hold a DB transaction across HTTP/Temporal calls.

Recheck stored 004 teacher role/access immediately before first remote start. Inactive/demoted owners keep the link `pending` and case `awaiting_workflow`; recheck each minute and start after restoration. For active owners, persist `starting` and `start_attempted_at`, then POST. A 200 matching **open** identity sets `started`, `run_id` and `started_at`; a matching closed response records `closed` and immediately applies the terminal reconciler rule below. An HTTP timeout/5xx/worker crash sets or leaves `uncertain`. Reconciler first GET-describes fixed ID: matching found adopts it, verified not-found within 30 days of `start_attempted_at` permits another POST with reject-duplicate policy, unavailable stays uncertain. A not-found result at or after 30 days is `history_missing` and never starts again. Stale `starting` lease is treated as uncertain. Never generate a new workflow ID, case ID or settings version. A mismatch is a fixed operator alert and no further start. After five minutes without start, progress derives `delayed=true`; after 24 hours it emits `workflow_start_overdue` alert but keeps retrying. No terminal case failure is inferred solely from a bridge outage. If Temporal reports a closed failed/cancelled run, or an unexpected `completed` run while the 007 case is still nonterminal, persist a single terminal safe `internal` event; never restart it. A later feature's proved terminal projection must be left intact. Keep namespace history long enough for pilot reconciliation (minimum 30 days); if it has expired while outcome remains uncertain, stop automatic start and raise `workflow_history_missing`, not a replacement run.

The workflow may publish `workflow_started` before the start POST response reaches Laravel. The callback may fill the pre-created link's run ID, mark the link `started` with `started_at`, and commit case version 2; a late matching start response must not overwrite it or regress a now-closed link. A mismatched run ID conflicts. Conversely, a start response alone does **not** advance the case to `queued`; the real worker callback does. Until then, teacher/admin see intake/queued and a possible delayed flag.

In 007, `CaseWorkflow.run` schedules and awaits the real `publish_workflow_started` activity, then parks at the extraction handoff with Temporal's deterministic `await workflow.wait_condition(lambda: False)`. This wait holds no activity worker or timer and 007 has no source signal handler, sender or source record. 008 owns the replay-compatible replacement of that line with real extraction/source activities and a `source_activation_v1` signal carrying exactly `{case_id:UUID,activation_id:UUID}`. 008 must deploy its compatible worker first, persist and authorize the activation ID in its own feature, then deliver the signal through its own authenticated path; its activity verifies that record before any source effect. Its tests replay an already-started 007 history, reject stale/foreign/duplicate activation and observe actual source work. No synthetic extraction activity or production signal sender is added by 007.

## Transactional milestone projection

After signature and strict schema validation, the projector locks the case and link, verifies fixed workflow ID/run ID/captured settings ID, then checks `(case_id,event_key)` **before** expected version. If key already exists with the same canonical payload digest, return prior event/version; if payload differs, 409 `event_conflict`. Otherwise require `expected_state_version == case.state_version`, supported event/type/status combination and allowed case transition. Insert immutable event with `sequence=old_version+1`, update case `state_version` and state (`queued`, `running`, `blocked`, `failed`), update link's safe projection and commit in one transaction. DB uniqueness on `(case_id,event_key)` and `(case_id,sequence)` is the final race guard. A losing concurrent request rereads only its exact duplicate; otherwise returns 409. DB failure rolls back both case and event and returns 503; activity retries the same key. No bulk write may alter 006 owner/Document/settings/action/idempotency fields.

`awaiting_workflow → queued` is permitted only for `workflow_started`; a verified closed Temporal failure before its first callback permits `awaiting_workflow → failed` with deterministic `temporal_closed:{run_id}`; `queued → running|blocked|failed`, `running → running|queued|blocked|failed`, and `blocked|failed` are terminal in 007 until an audited 014 retry policy is added. `queued → queued` is allowed for a distinct stage-completed milestone; version still increments. Do not require monotonic stage rank: later per-unit work may revisit stages. 007 rejects worker `teacher_review`, `complete`, `awaiting_review`, `approved`, `cancelled` transitions until 012–014 add proof-bearing producers. A closed Temporal failure reconciler uses deterministic event key `temporal_closed:{run_id}` and current version under lock; if the same closure was recorded, no-op. An open workflow with no worker is delayed, not failed.

## Captured retry policy and review gate

Before bridge start, Laravel calls `SettingsVersionRepository::getCaptured(case.settings_version_id)` and verifies its checksum, then sends only the immutable retry fields and checksum in the signed command. Missing/corrupt captured settings leaves the case/link pending with a fixed `settings_unavailable` alert and no remote start. Recovery restores the exact captured row/bytes from trusted backup under 005's immutable-version rules; never switch to the active pointer or publish a replacement version for this case. The Python workflow uses the input snapshot on every activity/replay; it never reads active settings. For a retryable 007 callback activity use Temporal `RetryPolicy(initial_interval=retry_delay_seconds,backoff_coefficient=2.0,maximum_interval=3600 seconds,maximum_attempts=technical_retries+1)` with `start_to_close_timeout=15 seconds`. `technical_retries=0` means one attempt. A typed `ApplicationError(non_retryable=True)` for invalid contract/policy is not retried. HTTP timeout/503 is retryable; 409 changed event/stale is nonretryable after exact duplicate reconciliation. Workflow-level retry policy is unset so exhaustion does not create a new run. On callback exhaustion Temporal closes failed; Laravel reconciler records safe `internal` or `provider_unavailable`, not raw exception. Later 008–012 activities must implement their own external-effect idempotency; Temporal replay alone is insufficient.

`ReviewGate` in `v3_engine/workflows/review_gate.py` is reusable deterministic workflow code, tested through a **test-only** workflow. Its `enter(candidate_ref,candidate_version)` input later comes from 012's persisted passing qualification; its decision signal later comes only from 013's committed, active original-teacher decision. It stores one current opaque candidate ref/version and one accepted decision ID/outcome (`approve|request_changes`); exact duplicate signals leave state unchanged, while stale version, different candidate or reused decision ID with changed outcome are ignored and cannot release the wait. `await workflow.wait_condition(...)` waits without an activity worker; an SDK query exposes only candidate ref/version and consumed decision ID for 013's reconciliation. 007 adds no production teacher review route, ReviewSignal table, candidate model, review note field or signal HTTP bridge route. Test fixtures may call Temporal directly; they do not establish live 013 authorization. 013 must add its own transactional decision/outbox and authenticated signal gateway, then test candidate qualification, owner recheck, stale version and uncertain delivery.
